# pssid_config.json

The single configuration file the pSSID daemon reads. Generated by the pSSID
GUI, delivered to `/etc/pssid/pssid_config.json` on each probe.

Every probe receives the **same** file. Each one works out which parts apply to
it by matching its own hostname.

## Top-level structure

```json
{
  "hosts":         [ … ],
  "host_groups":   [ … ],
  "archivers":     [ … ],
  "schedules":     [ … ],
  "ssid_profiles": [ … ],
  "tests":         [ … ],
  "jobs":          [ … ],
  "batches":       [ … ]
}
```

The model composes bottom-up:

```
test      one measurement (http, throughput, latency, …)
  ↓
job       an ordered set of tests, run in parallel or in series
  ↓
batch     jobs + which SSID profiles to join + which interface + a schedule
  ↓
host      which batches this probe runs
```

## `hosts`

```json
{
  "name": "198.111.226.184",
  "batches": ["batch_A"],
  "data": { "interface": "wlan0", "facility": "host_facility" }
}
```

| Field | Meaning |
|---|---|
| `name` | Must equal the probe's `hostname`. |
| `batches` | Batches this probe runs. |
| `data` | Key/value metadata, used for variable substitution. |

**`name` must match the probe's hostname exactly.** If no host entry matches,
the daemon logs `No host with name '…' found.` and **exits 1** - the probe does
not start.

## `host_groups`

Batches and metadata applied to several probes at once.

```json
{
  "name": "rpi4",
  "batches": ["batch_http_google"],
  "hosts": ["198.111.226.182"],
  "hosts_regex": [".*184"],
  "data": { "facility": "group_facility" }
}
```

A probe joins a group if its hostname is listed in `hosts` **or** matches any
pattern in `hosts_regex`.

> `hosts_regex` uses `re.match`, which anchors at the **start** only. `probe`
> matches `probe-1`; it is a prefix match, not a full match. Anchor with `$` if
> you mean the whole name.

A probe's batches are the union of its own and every group it belongs to.

### Metadata precedence

Host metadata **wins** over group metadata. Keys are resolved first-write-wins,
and the host's `data` is applied before any group's - so a key defined in both
resolves to the host's value.

## `schedules`

```json
{ "name": "every_two_minutes", "repeat": "*/2 * * * *" }
```

`repeat` is a standard five-field cron expression.

A batch may reference several schedules; the daemon computes the next fire time
for each and runs the batch at the **earliest**. It reschedules after every run,
so a batch is queued at most once at a time.

A batch with no resolvable schedule is never queued. It logs a warning and sits
idle - valid, loaded, and never running.

## `ssid_profiles`

```json
{
  "name": "MWireless",
  "ssid": "MWireless",
  "test_level": "SSID",
  "bssid_scan": "Disabled",
  "min_signal": -79
}
```

`name` is the identifier used everywhere else, including the credential file
name: profile `MWireless` requires
`/etc/wpa_supplicant/wpa_supplicant_MWireless.conf`. See
[wpa_supplicant](config-wpa-supplicant.md).

`ssid` is the actual broadcast network name. They are often the same, but they
are not required to be, and only `name` determines the filename.

## `tests`

```json
{ "name": "http_google", "type": "http", "spec": { "url": "www.google.com" } }
```

`type` selects the pScheduler test plugin; `spec` is passed through to it.

## `jobs`

```json
{
  "name": "job_A",
  "parallel": "True",
  "tests": ["throughput_arbl", "http_google"],
  "continue-if": "false"
}
```

> **`parallel` and `continue-if` must be JSON *strings*, not booleans.**
>
> The daemon compares `parallel` against the exact strings `"True"` and
> `"False"`, and calls `.lower()` on `continue-if`. A real JSON boolean
> (`true`) fails the first silently - the value reaches pScheduler as an
> unconverted string - and crashes the second with an `AttributeError`.
>
> Note the capitalisation: only `"True"`/`"False"` convert. `"true"` stays a
> string. The GUI emits the correct form; this matters when hand-editing.

## `batches`

```json
{
  "name": "batch_A",
  "priority": 1,
  "test_interface": "$interface",
  "ssid_profiles": ["MWireless"],
  "schedules": ["every_two_minutes", "every_three_minute"],
  "jobs": ["job_A"],
  "archivers": ["syslog"]
}
```

| Field | Meaning |
|---|---|
| `priority` | Tie-break when two batches are due at once (lower runs first). |
| `test_interface` | The wireless interface, or a `$variable`. |
| `ssid_profiles` | Profiles to join, in order. Each needs its own conf file. |
| `schedules` | Earliest next-run wins. |
| `jobs` | Jobs to run once associated. |

## Variable substitution

A string value containing `$` is replaced from the metadata resolved for this
probe. In the example above, `"test_interface": "$interface"` becomes `"wlan0"`
from the host's `data.interface`.

Four rules are worth knowing, because they are surprising:

1. **Keys containing `name` are skipped entirely.** `batch_name`, `hostname` and
   anything else with `name` in the key is never substituted - and never
   reported as unresolved either.
2. **Matching is on the *value*, as a substring.** A metadata key matches if it
   appears anywhere inside the value string. A short key like `face` will match
   `$interface`, so choose metadata names that will not collide.
3. **Substitution replaces the whole value - it does not interpolate.**
   `"$interface-monitor"` becomes `"wlan0"`, not `"wlan0-monitor"`. Composite
   values silently lose everything but the substituted part.
4. **Unresolved variables invalidate the batch.** If a `$` survives, the daemon
   logs `has unresolved variables` and refuses to run the batch. (Placeholders
   nested inside a sub-object are not currently detected, and pass through
   literally.)

## Validation

The GUI validates before writing the file. To check what a probe actually holds:

```bash
# Well-formed JSON?
jq empty /etc/pssid/pssid_config.json && echo "valid JSON"

# Full daemon-side validation, without running anything
sudo pssid-daemon.py --config /etc/pssid/pssid_config.json --validate
```

`--validate` loads the file, resolves this host, transforms every batch and
reports problems, then exits before scheduling. It is the closest thing to a
dry run.

Frequent mistakes it catches:

- A hostname that does not match any `hosts` entry.
- A batch referencing an undefined job, test or schedule.
- A batch with an empty `ssid_profiles`.
- `parallel` or `continue-if` sent as booleans.
- A `$variable` with no matching metadata.

It cannot tell you whether the credentials work, whether the interface exists,
or whether the conf files are present - those are probe-side facts. See
[wpa_supplicant](config-wpa-supplicant.md).

## Delivery

The GUI writes `pssid_config.json` and `hosts.ini` to `/var/lib/pssid/output/`
on the controller. Delivery to probes is a separate, host-side step:

```bash
sudo scripts/provision-probes.sh                  # every probe
sudo scripts/provision-probes.sh --limit rpi4     # one host group
sudo scripts/provision-probes.sh --dry-run        # show the plan
```

The file is copied to a temporary name and moved into place atomically, so a
probe never reads a half-written config.

This reports **delivery only**. Whether the daemon adopted the file is not
observable from the controller.
